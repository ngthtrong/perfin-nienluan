\chapter{Installation Guide}

The minimum environment is Node.js/npm, PostgreSQL and Expo Go or a browser. Redis 7 is recommended for the worker. Without Redis, the API may use an in-memory KV fallback during development, but queue and retry behaviour is not demonstrated.

\section{Backend Setup}

From the project root, copy the sample configuration, supply PostgreSQL settings and retain \code{AI_PROVIDER=local} when no Gemini key is used. Never commit secrets or service-account files.

\begin{verbatim}
cd demo/backend
cp .env.example .env
npm install
npm run migrate
npm start
\end{verbatim}

The API defaults to \url{http://127.0.0.1:3000}. Use that URL for a basic availability check. Recreate schema and seed data only on a development/test database:

\begin{verbatim}
npm run migrate:fresh
\end{verbatim}

\section{Redis and Worker}

From \code{demo}, start Redis with Docker Compose and open another terminal for the worker:

\begin{verbatim}
docker compose up -d redis
cd backend
npm run worker
\end{verbatim}

Verify \code{REDIS_URL}, \code{JOBS_ENABLED} and timezone in \code{backend/.env}. \code{docker compose down} stops Redis while retaining its volume.

\section{Frontend Setup}

\begin{verbatim}
cd demo/frontend
npm install
EXPO_PUBLIC_API_URL=http://127.0.0.1:3000 npm start
\end{verbatim}

For a phone on the same LAN, replace \code{127.0.0.1} with the backend host's LAN address and use \code{npm run start:lan}. If the device cannot reach that address, use Expo tunnel plus a separate backend tunnel. Never expose AI secrets through frontend environment variables.

\chapter{Quick User Guide}

\begin{enumerate}
  \item Open the application and check that Dashboard shows balance, total income/expense and recent transactions.
  \item Add a transaction from Transactions, or open Chat and enter a sentence such as ``ăn phở 50k sáng nay''.
  \item For image/audio, review and edit the OCR text or transcript. Media results are not stored automatically.
  \item Review amount, type, date, category and wallet in the preview; edit, cancel or confirm. Only confirmation creates a transaction.
  \item Use Budget for limits, Reports for trends/insights and Goals for plans and what-if scenarios.
  \item Correct an incorrect category. Confirmed corrections may be retrieved for a later input.
\end{enumerate}

The prototype has no login and uses \code{default_user}. Do not enter sensitive data or treat results as guaranteed investment advice.

\section{Classification and correction retrieval}
\label{app:classification-algorithms}

\subsection{Normalization and category scoring}

\code{normalizeForMatch} applies Unicode NFD, removes diacritics, maps \code{đ/Đ} to \code{d/D}, lowercases, replaces non-alphanumeric runs with spaces, and collapses repeated spaces. Thus ``  Điện-thoại! '' becomes \code{dien thoai}. Exact, alias and fuzzy comparisons all use the normalized string and consider only the same \code{type} when the caller provides a transaction type.

For two normalized strings, the matcher computes three scores:

\begin{enumerate}
  \item \textbf{Edit score:} $s_{edit}=1-d_{lev}(u,v)/\max(|u|,|v|)$, where $d_{lev}$ is Levenshtein distance.
  \item \textbf{Dice score:} twice the number of overlapping tokens divided by the number of distinct tokens in the two token sets, then multiplied by $0.92$.
  \item \textbf{Containment score:} when the smaller token set is contained in the larger and has at least two tokens, use $\min(0.94,0.82+0.12|U|/|V|)$; otherwise use 0.
\end{enumerate}

The final score is

\begin{equation}
  s=\max(s_{edit},\;0.92s_{dice},\;s_{contain}).
\end{equation}

The decision pipeline is:

\begin{enumerate}
  \item Scope categories by transaction type and select the ``Khác'' fallback (or the first category if that fallback is absent).
  \item If a normalized category name equals the input, return \code{exact} with confidence 1.
  \item If exactly one alias equals the input, return \code{alias_exact} with confidence 0.98; aliases resolving to multiple categories return the fallback with reason \code{ambiguous_alias}.
  \item Rank fuzzy scores over each category name and its aliases. Inputs longer than four characters require $s\geq0.82$; inputs of at most four characters require $s\geq0.90$. If a runner-up exists, the score gap must be at least $0.08$.
  \item If the threshold or margin is not met, return the fallback with reason \code{below_threshold} or \code{ambiguous_fuzzy}; do not silently choose the nearest candidate.
\end{enumerate}

For ``ăn uốg'', normalization gives \code{an uog}; relative to \code{an uong}, Levenshtein distance is 1 over length 7, so $s_{edit}=6/7\approx0.857$. The score exceeds the 0.82 threshold and, without a competing candidate, returns ``Ăn uống'' with \code{matchKind=fuzzy}. In contrast, the alias ``điện thoại'' points to both ``Điện tử'' and ``Hóa đơn \& Dịch vụ'' and must return ``Khác'' for clarification.

Phrase alias lookup also requires word boundaries. When several aliases match, the alias with more tokens wins; a tie in token count and length across different categories returns \code{ambiguous_alias}. This prevents a short alias such as ``an'' from matching inside ``quần áo''.

\subsection{Correction ranking}

A correction is useful only when a log has \code{feedback_type=classification}, original text and a corrected category different from the original category. The label key prioritizes \code{type + normalized category name}; an id is used only when the name is absent. The service loads at most 200 recent candidates from the current profile.

For every candidate, the service computes \code{textSimilarity}, keeps an exact match with score 1 or a fuzzy match with a minimum score of 0.88, and removes a different income/expense type. Candidates are grouped by corrected label:

\begin{equation}
  w_k=\sum_{j\in k}s_j,\qquad
  agreement=\frac{\max_k w_k}{\sum_k w_k}.
\end{equation}

The winning candidate exposes \code{support} (group count), \code{bestScore} (maximum score) and confidence rounded from $s_{best}\times agreement$. Retrieval is rejected when:

\begin{itemize}
  \item the input is empty or no candidate reaches the threshold;
  \item identical normalized text has multiple corrected labels;
  \item the non-exact winner is below 0.88;
  \item a competing label leaves agreement below 0.8;
  \item a legacy log lacks \code{type} while the caller requests a specific type.
\end{itemize}

Few-shot examples use a separate policy: at most five by default, an absolute limit of 20, and a minimum score of 0.35. Conflicting labels for the same typed normalized input are discarded, and duplicate labels keep only the nearest example. Correction therefore is not majority voting and cannot change transaction type.

Normalization, typo, ambiguous alias, exact/fuzzy correction, label conflict and name-only/id+name cases are covered by \path{feedback.test.js}. Coverage, helped/harmed/net and group-split metrics are covered by \path{experiment-metrics.test.js}.

\section{Financial analysis algorithms}
\label{app:analytics-algorithms}

\subsection{Calendar axes and runway}

The helpers create an axis first, initialize totals to zero, and then add rows that fall within that axis:
\begin{itemize}
  \item \code{completeDailyTotals} completes the day axis;
  \item \code{completeMonthlyByCategory} completes each category's month axis;
  \item \code{completeWeeklyByCategory} completes the completed ISO-week axis.
\end{itemize}
Correlation uses completed ISO weeks; the week containing today is excluded. This preserves the denominator when a category is inactive during a period.

Runway first filters wallets to \code{currency=VND} and types \code{cash}, \code{bank} and \code{e_wallet}:

\begin{equation}
  B=\sum_{w\in\text{eligible wallets}} balance_w.
\end{equation}

For a 14-day window and daily expense $e_j$ (zero-spend days remain zero),

\begin{equation}
  \bar e_W=\frac{1}{W}\sum_{j=1}^{W}e_j,
  \qquad d=\left\lfloor\frac{B}{\bar e_W}\right\rfloor.
\end{equation}

If $B\leq0$, the result is $d=0$ with \code{alreadyDepleted}; if $\bar e_W\leq0$, the result has \code{daysLeft=null} and no depletion date is invented. Payday is only a comparison warning for the next occurrence; day 31 is clamped to the last day of the target month.

For two liquid VND wallets totaling 300,000 VND and 14 days each spending 100,000 VND, $\bar e_W=100,000$ and $d=3$. USD and investment wallets do not increase $B$.

\subsection{Trend and anomaly}

For a zero-filled series $y_0,\ldots,y_{n-1}$, OLS uses $x_i=i$, $\bar x$ and $\bar y$ to calculate

\begin{equation}
  b=\frac{\sum_i(x_i-\bar x)(y_i-\bar y)}{\sum_i(x_i-\bar x)^2},
  \qquad a=\bar y-b\bar x.
\end{equation}

It computes the fit statistic $R^2=1-SS_{res}/SS_{tot}$. The next-step forecast is $\max(0,\operatorname{round}(bn+a))$. Money slope/intercept are rounded and $R^2$ is rounded to three decimals. The engine emits a trend only with at least three positive-spend months, $b>0$, $R^2\geq0.5$ and an average stepwise percentage change of at least 10\% over steps with a positive preceding value. A constant series has $R^2=0$ and produces no signal.

Anomaly detection uses the mean, sample standard deviation and interpolated quantiles over the complete 30-day axis:

\begin{equation}
  z_i=\frac{e_i-\bar e}{s},
  \qquad upperFence=Q_3+1.5(Q_3-Q_1).
\end{equation}

Only the upper tail is flagged when $z_i\geq2.5$ or $e_i>upperFence$, and the engine requires at least four positive-spend days before calling the helper. When $s=0$, $z_i=0$; when $IQR=0$, the IQR branch is disabled. In the synthetic sample $[100,100,100,1000]$, $Q_1=100$, $Q_3=325$ and the upper fence is 662.5, so 1000 is flagged by IQR even though its z-score is below 2.5.

\subsection{Recurring and day-of-week analysis}

Recurring discovery removes diacritics, lowercases, removes digits from descriptions and groups positive expense transactions by normalized description. A group needs at least three occurrences, every amount must be within 15\% of the mean, and positive date gaps must have population coefficient of variation at most 0.12. All gaps must fit one cadence:

The output keeps the latest description, occurrence count, average amount, cadence, \code{lastSeen}, \code{nextExpected} and \code{monthlyEstimate}; there is no default amount ceiling. Three 900,000 VND payments approximately one quarter apart therefore remain a quarterly recurring item estimated at 300,000 VND/month.

Day-of-week analysis uses spending per active day in the 60-day window; an inactive day is not treated as a zero-spend observation. It needs at least four observed weekdays and a peak-to-mean ratio of 1.8; otherwise it returns \code{null}.

\subsection{Correlation}

The engine creates a shared axis of 12 completed ISO weeks, zero-fills each category and keeps categories observed in at least four weeks. Pearson uses the shorter series length but returns \code{null} for fewer than three paired observations or zero variance:

\begin{equation}
  r=\frac{\sum_i(x_i-\bar x)(y_i-\bar y)}
  {\sqrt{\sum_i(x_i-\bar x)^2\sum_i(y_i-\bar y)^2}}.
\end{equation}

The engine scans every pair, keeps $r\geq0.6$ and returns the pair with the greatest $r$. For proportional series $[100,200,300,400]$ and $[200,400,600,800]$, $r=1$; the result describes co-movement in the selected window and does not imply causation.

\section{Budget and financial-goal planning}
\label{app:planning-algorithms}

\subsection{History summary and budget recommendation}

\code{summarizeHistory} normalizes periods to \code{YYYY-MM}, aggregates income by month and aggregates expense by category id (or normalized name). With \code{expectedPeriods}, every listed month remains in the denominator even if it has no transaction. Thus a category spending 3,000,000 VND in one month of a three-month window has \code{average_spend=1,000,000}.

Each category is assigned to \code{needs} or \code{wants}; the default needs set contains food, transport, health, education, housing, bills/services and groceries, while \code{groupOverrides} can replace the assignment. With buffer $q$ over $m$ months,

\begin{equation}
  b_c=(1+q)\frac{1}{m}\sum_{j=1}^{m}s_{c,j}.
\end{equation}

The progress forecast receives \code{spent}, \code{amount_limit} and the target period. For the current month, $d_e=\max(1,\text{today's day})$; for a historical month, $d_e$ is the full month length. If $D$ is the number of days in the month,

\begin{equation}
  \widehat S_D=\operatorname{round}\!\left(\frac{S}{d_e}D\right),
  \qquad dailyRate=\operatorname{round}\!\left(\frac{S}{d_e}\right).
\end{equation}

The result records:
\begin{itemize}
  \item \code{daily_rate}, \code{projected_spend} and projected percentage;
  \item the \code{likely_to_exceed} flag and, when applicable, \code{projected_exceed_day}.
\end{itemize}
When the limit is positive and current spending is below it, the service returns an exceedance day only if it remains in the month; a zero limit does not create a fictitious day. For 2,000,000 VND spent on day 10 of a 30-day month with a 5,000,000-VND limit, the rate is 200,000 VND/day, the forecast is 6,000,000 VND and the projected exceedance day is 25. The corresponding cases are in \code{budget-forecast.test.js}.

The strategies behave differently:

\begin{itemize}
  \item \textbf{category average:} uses $b_c$ directly.
  \item \textbf{50--30--20:} allocates group caps by each category's share of $b_c$, with default needs, wants and savings caps of $0.5I$, $0.3I$ and $0.2I$.
  \item \textbf{hybrid:} keeps $b_c$ when the group total is within its cap; otherwise it scales all group items by $cap/groupAverage$.
\end{itemize}

Each raw limit is rounded by \code{roundingIncrement}, 10,000 VND by default. \code{enforceRoundedCap} then repeatedly reduces one increment from a positive category with the largest overshoot until the group total is within its cap. A sum \code{needsRate+wantsRate+savingsRate} above 1 is rejected; missing income falls back to \code{category_average} with a warning.

For history with 10,000,000 VND monthly income, 4,000,000 VND needs and 4,000,000 VND wants over three months, with zero buffer, 50--30--20 gives caps of 5,000,000 and 3,000,000 VND. Hybrid keeps needs at 4,000,000 but shrinks wants to 3,000,000. If two wants categories are 15,000 VND each, a 10,000-VND rounding increment and a 30,000-VND cap still produce a post-reconciliation total within the cap.

\subsection{Saving, debt payoff and what-if}

For a saving/purchase goal, validation requires a positive target, non-negative current amount and a finite non-negative contribution. If contribution is \code{null}, the planner uses available surplus; an explicit user contribution of zero remains zero rather than being replaced by surplus. With remaining amount $R=\max(0,target-current)$ and monthly contribution $M>0$,

\begin{equation}
  n_s=\left\lceil\frac{R}{M}\right\rceil,
  \qquad projectedDate=addMonthsClamped(today,n_s).
\end{equation}

End-of-month dates are clamped, so 31/01 plus one month becomes 28/02. If $R=0$, the planner returns completed with horizon 0; if $M=0$, horizon and projected date are \code{null} with \code{NO_MONTHLY_CONTRIBUTION}. A future deadline uses at least one contribution period in the same calendar month and reports \code{requiredMonthly}, gap and shortfall.

For current principal $L$, nominal annual percentage rate $i$ and $r=i/(12\times100)$, the level end-of-month payment over $n_d$ months is

\begin{equation}
  P=\begin{cases}
  \dfrac{Lr}{1-(1+r)^{-n_d}}, & r>0,\\[6pt]
  \dfrac{L}{n_d}, & r=0.
  \end{cases}
\end{equation}

Without a deadline, the planner simulates each month: add interest, subtract a payment no larger than the amount due, and stop at zero balance or the horizon (600 months by default; validation permits at most 1200). A zero payment returns \code{NO_MONTHLY_PAYMENT}; a payment no larger than first-month interest returns \code{NEGATIVE_AMORTIZATION}; an unpaid balance after the horizon returns \code{MAX_HORIZON_EXCEEDED}. For $L=10,000$, 12\% annual interest and payment 1,000, the result is 11 months and 589.85 total interest; payment 100 is rejected because the balance does not decrease.

What-if accepts only saving or purchase plans, validates non-negative extraMonthly, and reruns the planner with original contribution plus the extra amount. It returns the new contribution, new horizon, months saved, feasibility transition and shortfall; it does not persist a goal or change a debt plan.

The \code{window} object records size, unit and whether zero-fill was used; selected components add \code{category_count}, \code{wallet_count} or \code{observed_period_count}. Facts are cached for 600 seconds and reused only when schema, currency and payday context still match.

The numeric boundary is: SQL/Model reads source data, Analytics Engine computes facts, and only then does the narrator receive them. The LLM cannot call models, replace numbers, write transactions or turn \code{null} into a concrete value. A persona changes tone only when consent is enabled. A numeric grounding checker covering every numeric expression remains target design, not a measured result.
